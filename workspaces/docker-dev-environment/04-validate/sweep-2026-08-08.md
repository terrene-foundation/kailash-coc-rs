## 5. Decision points

### D1 — Close #89, or hold it until loom ingests?

**Recommend: close it, with a receipt comment naming the three ACs and the measuring commands.**
All three acceptance criteria were measured met last session; the "AC-1 remains open" comment
was refuted by measurement (the helper landed three days before the comment claiming otherwise).
The only residual is loom ingest, which is tracked by the proposal manifest — not by this issue.

**Cons, honestly:** the issue is the most legible pointer to that fixture's history, and closing
it moves that history one click further away. It also carries the `bug` label, so closing it
slightly understates how much loom-side work remains. Against that: an issue whose ACs are all
met is a false open, and a queue that carries false opens teaches readers to skim it.

**This needs a user gate** — `value-prioritization.md` MUST-4 forbids the agent closing a
value-bearing item unilaterally.

### D2 — Should anything be done locally at all, given the queue is empty?

**Recommend: no. Stop here and let loom drain.** The honest state is that this repo has no
durable work left. Manufacturing local `.claude/` fixes would be actively harmful — they are
Class-A, they get rebuilt away, and two sessions were already spent recovering from exactly
that class of loss.

**Cons:** a session that stops with items open _feels_ incomplete, and there is always more
diagnosis available (validators 16/18/15 have never run — see below). Against that: diagnosis
without a durable landing surface produces proposal entries for a queue that is already the
bottleneck at 92.

**One genuine exception, if you want a next thing:** validators **16, 18 and 15** have never
run at this tier, because `emit.mjs:3060` exits on the V14 failure before reaching them. Their
status is **UNKNOWN, not passing.** That is diagnosis with real information value and no
