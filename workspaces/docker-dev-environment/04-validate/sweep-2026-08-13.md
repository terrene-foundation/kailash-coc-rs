**This is self-inflicted.** Gate C was made a REQUIRED check yesterday (PR #143). ## 5. Decision points

### D1 — What to do with the inbound sync (PR #150)

Gate A flags 84 files, 0 acknowledged. Three dispositions, none self-decidable:

**(a) Re-apply the local fixes on top of the incoming version, in this PR.** Preserves the work; costs a reconciliation pass over 84 files.
_Pros:_ nothing is lost; the sync lands complete. _Cons:_ ~84 files of manual merge; several are files whose upstream version may legitimately supersede ours (they may be the very fixes we filed as proposals, now returning canonically).

**(b) `ACK-DISCARD:` the paths whose upstream version is genuinely canonical, re-apply the rest.** The gate's own sanctioned path for a deliberate, reviewed discard.
_Pros:_ correct in principle — some of these 84 SHOULD be discarded, because we filed them upstream and they are coming back fixed. _Cons:_ requires per-file adjudication of "did our fix land upstream, or is this a regression?" — that is the real work, and it is not mechanical.

**(c) Hold the sync until BUG-1 is fixed.** Gate C's failure is unrelated noise; clearing it first makes the board legible.
_Pros:_ separates the two red checks so Gate A's 84 findings are the only signal. _Cons:_ delays the delivery this repo has waited on all cycle.

**Recommendation: (c) then (b).** Fix BUG-1 first — it is ~0.5 cycle, entirely ours, and until it lands every sync PR is red for a reason that has nothing to do with the sync. Then adjudicate Gate A's 84 with a clean board. Taking (b) now means doing the per-file judgment against a board that is red for two unrelated reasons, which is how the wrong file gets acknowledged.

**Con of the recommendation, honestly:** it defers loom's delivery by one cycle, and this is the delivery every prior sweep said was the bottleneck. If the priority is landing the sync today, (b) is defensible — but the per-file adjudication should then be explicit about which of the 84 are returning-canonical vs genuine regressions.
